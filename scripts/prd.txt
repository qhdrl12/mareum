LangGraph 기반 AI 에이전트 배포 플랫폼 PRD (v1.0: ReAct 에이전트)
1. 개요
1.1. 배경:
최근 AI 기술, 특히 LLM(대규모 언어 모델)을 활용한 애플리케이션 개발이 활발해지면서, 개발자들은 보다 지능적이고 자율적인 AI 에이전트를 구축하고자 합니다. LangChain과 LangGraph는 이러한 에이전트, 특히 복잡한 워크플로우를 구현하는 데 강력한 도구를 제공합니다. 그러나 개발자가 LangGraph 에이전트를 설계하고 이를 실제 서비스 가능한 API로 만들어 배포하는 과정은 여전히 많은 시간과 노력을 요구합니다. 특히, 반복적인 FastAPI 서버 구축, Docker 패키징, 배포 작업은 개발 생산성을 저해하는 요인이 됩니다. Dify와 같은 플랫폼이 존재하지만, 프로토타이핑 단계를 넘어선 정교한 커스터마이징이나 사내 시스템과의 유연한 연동에는 한계가 있습니다.

1.2. 목표:
본 플랫폼은 개발자가 YAML 또는 JSON 형식의 설정 파일을 통해 ReAct(Reasoning and Acting) 에이전트의 핵심 구성 요소(LLM, 도구, 메모리, 프롬프트 등)를 정의하면, 이를 LangChain/LangGraph 기반의 ReAct 워크플로우로 자동 구축하고, FastAPI 기반 API로 패키징하여 Docker 컨테이너로 배포하는 것을 목표로 합니다. 이를 통해 개발자는 인프라 관리 부담 없이, 검증된 ReAct 패턴을 활용하여 신속하게 AI 에이전트를 개발하고 서비스에 통합할 수 있습니다.

1.3. 대상 사용자:
사내 AI 애플리케이션 또는 LLM 기반 기능을 개발하는 모든 개발자.

1.4. 기대 효과:
ReAct 에이전트 신속 구현: 검증된 ReAct 패턴 기반의 에이전트를 YAML/JSON 설정만으로 빠르게 구축하고 배포할 수 있습니다.
개발자 자유도 보장: Dify와 같은 프로토타이핑 도구보다 높은 수준의 커스텀 도구 연동 및 LLM, 프롬프트 설정을 통해 원하는 ReAct 에이전트를 구성할 수 있습니다.
신속한 배포 및 운영 효율화: 정의된 에이전트를 자동으로 API화하고 Docker 기반으로 배포하여, 개발자가 인프라 관리 부담 없이 빠르게 서비스를 출시하고 표준화된 방식으로 운영할 수 있도록 합니다.
기술 내재화 및 표준화: 핵심 AI 에이전트 기술을 내재화하고, 사내 표준 개발/배포 프로세스를 확립하여 장기적인 기술 경쟁력을 확보합니다.

2. 주요 사용자 요구사항
간편한 에이전트 정의: 개발자는 LLM, 도구, 시스템 지침과 같은 에이전트의 핵심 구성 요소를 YAML 같은 간단한 설정 파일로 정의할 수 있어야 합니다. 이를 통해 반복적인 설정 코드 작성 부담을 줄이고, 에이전트의 핵심 로직과 기능 구현에 더 집중할 수 있습니다.
자동화된 워크플로우 구축: 개발자가 정의한 설정을 기반으로, 플랫폼은 검증된 ReAct 패턴의 LangGraph 워크플로우를 자동으로 구축해야 합니다. 이를 통해 개발자는 LangGraph의 복잡한 내부 구조를 깊이 학습하지 않고도 강력한 추론 및 실행 능력을 갖춘 에이전트를 쉽게 활용할 수 있습니다.
신속하고 간편한 배포: 개발자는 설정 파일을 제출하는 것만으로 에이전트를 즉시 호출 가능한 API 엔드포인트로 배포할 수 있어야 합니다. 서버 설정, Docker 패키징, 인프라 배포 등 번거로운 과정을 플랫폼이 자동으로 처리하여, 아이디어를 빠르게 테스트하고 서비스에 적용할 수 있도록 지원해야 합니다.
유연한 커스텀 도구 연동: 개발자는 사내 API나 데이터베이스 조회 등 내부 시스템과 연동되는 자신만의 기능을 에이전트의 '도구'로 쉽게 등록하고 활용할 수 있어야 합니다. 이를 통해 에이전트가 실질적으로 유용한 작업을 수행하도록 확장할 수 있습니다.
명확한 동작 추적 및 디버깅: 플랫폼은 배포된 에이전트의 ReAct 과정(생각-행동-관찰)을 상세하게 추적하고 조회할 수 있는 로그 기능을 제공해야 합니다. 이를 통해 개발자는 에이전트의 동작을 쉽게 이해하고, 문제가 발생했을 때 신속하게 원인을 파악하고 해결할 수 있습니다.
통합 관리 대시보드: 개발자는 웹 기반 대시보드를 통해 자신이 배포한 모든 에이전트의 상태, API 엔드포인트, 사용량 등의 정보를 한눈에 파악하고 효율적으로 관리할 수 있어야 합니다.
손쉬운 에이전트 업데이트 및 관리: 개발자는 기존 에이전트의 프롬프트를 수정하거나 새 도구를 추가하는 등, 설정을 변경하고 이를 간편하게 재배포하여 에이전트를 지속적으로 개선하고 관리할 수 있어야 합니다.

3. 기능 요구사항
3.1. 에이전트 설정 (YAML/JSON)
스키마 정의: 플랫폼은 ReAct 에이전트 구성을 위한 명확하고 구조화된 YAML/JSON 스키마를 제공해야 합니다. 이 스키마는 버전 관리가 되어야 합니다.
입력 방식: 사용자는 웹 UI 또는 CLI를 통해 설정 파일을 업로드하거나, 웹 UI의 텍스트 편집기를 통해 직접 입력하고 유효성을 검사받을 수 있습니다.
구성 요소:
metadata: 에이전트의 고유 이름, 버전, 담당자, 설명 등 관리 정보.
agent_type: 에이전트 유형 (초기 버전에서는 react로 고정 또는 유일한 선택지).
model: 사용할 LLM 정의.
provider: OpenAI, Anthropic, Azure OpenAI, 사내 모델 등.
name: gpt-4o, claude-3-opus-20240229 등 모델명.
credentials_key: 사내 보안 저장소에 등록된 API 키 또는 인증 정보 참조 키.
parameters: temperature, max_tokens 등 LLM 호출 시 사용할 파라미터.
memory: (선택 사항) 사용할 메모리 유형 정의.
type: conversation_buffer 등 지원되는 메모리 유형.
config: 메모리 유형에 따른 설정 (e.g., max_history_length).
tools: 에이전트가 사용할 도구 목록.
name: 도구의 고유 이름.
description: LLM이 도구의 기능과 사용법을 이해할 수 있는 상세한 설명.
schema: 도구 입력값에 대한 JSON 스키마.
endpoint: 도구를 실행할 API 엔드포인트 및 HTTP 메소드 (또는 사내 등록된 함수 참조).
knowledge: (선택 사항) RAG(검색 증강 생성)에 사용할 벡터 DB 정보.
provider: Pinecone, ChromaDB, 사내 벡터 DB 등.
credentials_key: DB 연결 정보 참조 키.
collection_name: 사용할 컬렉션(인덱스) 이름.
search_config: 검색 시 사용할 파라미터 (e.g., top_k).
prompt: 에이전트 프롬프트 설정.
system_prompt: 에이전트의 역할, 목표, 제약 조건 등을 정의하는 시스템 프롬프트.
react_template: (선택 사항) 기본 ReAct 프롬프트 템플릿을 재정의하거나 커스터마이징.

3.2. LangGraph 워크플로우 구축
플랫폼은 입력된 YAML/JSON 설정의 유효성을 스키마에 따라 검사합니다.
유효한 설정이 확인되면, 플랫폼은 내부적으로 LangChain과 LangGraph를 사용하여 표준 ReAct 워크플로우를 생성합니다.
이 워크플로우는 '생각(Thought)', '행동(Action)', '행동 입력(Action Input)', '관찰(Observation)' 단계를 반복하며, 정의된 도구와 LLM을 사용하여 사용자의 요청을 처리하도록 구성됩니다.
플랫폼은 사전에 정의된 ReAct LangGraph 템플릿을 기반으로 하며, 사용자 설정(LLM, 도구, 프롬프트 등)을 이 템플릿에 동적으로 주입하여 최종 LangGraph 객체를 완성합니다.

3.3. FastAPI API 생성
플랫폼은 완성된 LangGraph 에이전트를 실행할 수 있는 FastAPI 애플리케이션을 자동으로 생성합니다.
이 애플리케이션은 최소한 다음과 같은 엔드포인트를 포함해야 합니다:
POST /invoke: 사용자의 입력을 받아 에이전트를 실행하고 최종 결과를 반환합니다.
GET /health: API 서버의 상태를 확인합니다.
API 요청/응답 본문은 표준화된 JSON 형식을 따릅니다.
API에는 인증/인가 메커니즘(e.g., API 키)이 적용됩니다.

3.4. Docker 기반 배포
플랫폼은 생성된 FastAPI 애플리케이션, LangChain/LangGraph 라이브러리, 기타 필요한 종속성을 포함하는 Dockerfile을 자동으로 생성합니다.
이 Dockerfile을 사용하여 Docker 이미지를 빌드하고, 에이전트 이름과 버전을 태그로 지정합니다.
빌드된 이미지를 사내 Docker 레지스트리에 푸시합니다.
사용자의 요청에 따라, 또는 자동으로, 사내 Kubernetes 클러스터나 지정된 Docker 호스트에 해당 이미지를 배포하고, 외부에서 접근 가능한 서비스(API 엔드포인트)를 생성합니다.

3.5. API 관리 및 사용
플랫폼은 웹 기반 대시보드를 제공하여, 사용자가 배포한 에이전트 목록, 각 에이전트의 상태(배포 중, 실행 중, 오류 등), API 엔드포인트 주소를 확인할 수 있게 합니다.
대시보드에서 각 API에 대한 접근 키를 발급받고 관리할 수 있습니다.
각 에이전트 API에 대한 간단한 테스트 UI를 제공하여, 웹 브라우저에서 직접 API를 호출하고 응답을 확인할 수 있게 합니다.
curl 예제나 Python 코드 스니펫 등 API 사용 가이드를 제공합니다.

3.6. 모니터링 및 로깅
배포된 각 에이전트 API의 기본 메트릭(호출 횟수, 평균 응답 시간, 오류율)을 수집하여 대시보드에서 시각화합니다.
LangGraph의 실행 추적(Trace) 기능을 활용하여, 각 API 호출 시 에이전트 내부에서 발생한 **ReAct 과정(Thought, Action, Observation)**을 상세하게 로깅합니다.
사용자는 대시보드를 통해 이러한 상세 로그를 검색하고 조회하여, 에이전트의 동작을 분석하고 문제를 해결할 수 있습니다.

4. 비기능 요구사항
성능 (Performance): 플랫폼 자체의 에이전트 빌드 및 배포 시간은 합리적이어야 합니다 (목표: 설정 제출 후 10분 이내 배포 완료). 배포된 API의 오버헤드는 최소화되어야 합니다.
확장성 (Scalability): 배포된 각 에이전트 인스턴스는 독립적으로 수평 확장이 가능해야 합니다 (e.g., Kubernetes HPA 연동). 플랫폼 자체도 사용자 및 배포 요청 증가에 대응할 수 있어야 합니다.
안정성 (Reliability): 플랫폼은 99.9% 이상의 가용성을 목표로 하며, 배포된 에이전트 API 역시 높은 안정성을 보장해야 합니다. 배포 실패 시 롤백 또는 재시도 메커니즘이 필요합니다.
사용성 (Usability): YAML/JSON 스키마는 명확하고 이해하기 쉬워야 하며, 관련 문서가 잘 제공되어야 합니다. 플랫폼 대시보드는 직관적이고 사용하기 편리해야 합니다.
보안 (Security): LLM/DB/Tool API 키 등 민감 정보는 안전하게 관리되어야 합니다. API 접근 제어는 명확해야 하며, 사내 보안 규정을 준수해야 합니다. 로깅 시 민감 정보 마스킹 기능이 필요합니다.

5. 가정 및 제약 조건
가정:
사용자는 ReAct 에이전트의 기본 개념과 작동 원리를 이해하고 있습니다.
사내에는 Docker 레지스트리 및 Kubernetes 또는 Docker 호스트 기반의 배포 인프라가 구축되어 있으며, 플랫폼과의 연동이 가능합니다.
LLM API, 벡터 DB, 사내 도구 API 등에 대한 접근 권한 및 인증 정보 관리 방안이 마련되어 있습니다.
제약:
초기 버전(v1.0)은 단일 ReAct 에이전트 생성 및 배포만 지원합니다. 다중 에이전트, 순차적/병렬적 에이전트 구성 등은 지원하지 않습니다.
사용자는 LangGraph의 노드(Node)와 엣지(Edge)를 직접 정의하거나 수정할 수 없습니다. 플랫폼이 제공하는 표준 ReAct 워크플로우만 사용 가능합니다.
지원되는 LLM, 메모리 유형, 벡터 DB는 플랫폼에서 사전에 정의된 목록으로 제한될 수 있습니다.

6. 성공 지표
플랫폼 활성화: 플랫폼을 통해 배포되어 활성 상태인 에이전트의 수.
배포 시간 단축: 개발자가 에이전트 설정을 완료한 후, 실제 사용 가능한 API 엔드포인트를 받기까지 걸리는 평균 시간.
개발자 만족도: 플랫폼 사용 용이성, 기능, 안정성 등에 대한 정기적인 개발자 설문조사 점수.
API 사용량: 플랫폼을 통해 배포된 모든 에이전트 API의 총 월간 호출 횟수.
오류율 감소: 배포된 에이전트 API의 평균 오류율 및 플랫폼 자체의 장애 발생 빈도.
